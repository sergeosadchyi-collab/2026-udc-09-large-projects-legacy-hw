# Де агент помилявся на legacy-коді

Нижче — реальні випадки з цієї сесії (Claude Sonnet 4.5 в agent mode, JetBrains
IDEA). Для кожного вказано, чи помилку спіймано **до** правки коду, чи вона
встигла нашкодити.

---

## Випадок 1 — «Здається, це одна функція». Пошук за іменем дав повну на вигляд і неправильну відповідь

- **Що просили:** знайти всі місця, чий результат зміниться, якщо змінити
  спільну функцію форматування дат (Task B, крок 1).
- **Що агент зробив:** першим інструментом запустив
  `grep -rn "formatDate" app/lib app/bin`. Результат — **два** споживачі:
  `lib/invoices/render.js:38-39` і `lib/notifications/reminders.js:40,46`.
  Це **точно збіглося з тікетом** («HTML-рахунок, а також листи-нагадування»),
  виглядало як повна відповідь і спокушало зупинитись.
- **Чому це помилка:** справжніх споживачів **три**. Третій —
  `lib/export/accounting.js:30`, нічний файл для «Облік-Плюс». Він бере
  форматер динамічно:

  ```js
  var render = format['format' + col.type];   // col.type = "Date" з config/export-columns.json
  ```

  Рядка `formatDate` у цьому файлі **немає взагалі**, тож текстовий пошук за
  іменем функції не побачить його ніколи.
- **Як помітили:** не повірив одному `grep`. Другий запит був не за іменем
  функції, а **за імпортом модуля**:

  ```
  $ grep -rn "require(.*format" app/lib app/bin
  lib/invoices/render.js:7
  lib/export/accounting.js:9      <-- третій, якого не було в першому списку
  lib/notifications/reminders.js:4
  ```

- **Чому агент так вирішив:** пошук за іменем — найдешевший і зазвичай
  достатній інструмент, а його результат тут ще й **підтверджував тікет**.
  Збіг із очікуванням — найгірший момент, щоб припинити перевірку.
- **Як виправили:** список споживачів будувався за графом імпортів, а потім
  перевірявся **виконанням коду**, а не читанням.

### Скільки б це коштувало — вимірювання, а не припущення

Щоб не гадати, я відтворив наївний шлях: підмінив `formatDate` у пам'яті на
`дд.мм.рррр` і збудував нічний файл. **Жодного файлу в репо не змінено** —
підміна працює саме тому, що `accounting.js` резолвить хелпер у момент виклику:

```js
// node scratch.js  (з теки app/)
var format = require('./lib/format');
var accounting = require('./lib/export/accounting');
var store = require('./lib/store');
var by = {}; store.loadSync('customers').forEach(function (c) { by[c.id] = c; });

format.formatDate = function (v) {          // «це ж одна функція»
  var p = String(v).slice(0, 10).split('-');
  return p[2] + '.' + p[1] + '.' + p[0];
};
var out = accounting.buildAccountingFile(store.loadSync('invoices'), by);
```

Результат:

```
ticket goal — invoice HTML:
  Сплатити до: <b>21.03.2026        <-- тікет виконано, замовник задоволений

Oblik-Plus export, first data row
  before: INV-2026-00001;03/01/2026;03/15/2026;10000001;...
  after : INV-2026-00001;01.03.2026;15.03.2026;10000001;...

rows in the nightly file        : 36
rows Oblik-Plus would now SKIP  : 36
export file changed             : true
```

**Усі 36 рахунків** не потрапили б у бухгалтерію. Без помилки, без листа —
за `app/docs/integrations/oblik-plus.md:27-35` їхній сервер такі рядки
**пропускає** і пише попередження у власний журнал, який ніхто не читає. Саме
так у лютому 2021 «втратили» 40 рахунків, і тести тоді були зелені.

**Спіймано до зміни коду.** Ціна перевірки — один додатковий `grep`.

## Випадок 2 — агент передбачив червоним тест, який навіть не перевіряє змінювану функцію

- **Що просили:** у `docs/impact.md` §5 описати наперед, які тести мають
  почервоніти після зміни й чому.
- **Що агент написав:** «Із засіяних тестів очікувано почервоніють
  `test/invoices.test.js:41-42` **і `test/format.test.js`**».
- **Чому це помилка:** `app/test/format.test.js` **не перевіряє `formatDate`
  взагалі**. У ньому лише `formatMoney`, `formatDecimal`, `formatText` і
  `formatPercent`. Жоден засіяний тест не покривав `formatDate` — при тому, що
  це функція з контрактом із зовнішньою системою.
- **Як помітили:** перед комітом Task B перевірив твердження пошуком літералів
  старого формату по всьому `app/test/`:

  ```
  $ grep -rn '03/' app/test | grep -v characterization
  test/invoices.test.js:41  assert.match(html, /Дата: <b>03\/09\/2026<\/b>/);
  test/invoices.test.js:42  assert.match(html, /Сплатити до: <b>03\/23\/2026<\/b>/);
  test/orders/routes.test.js:49  ... { from: '03/01/2026' } ... status, 400
  ```

  `format.test.js` у списку немає.
- **Чому агент так вирішив:** **вивів зі схожості імен**, а не з коду: файл
  зветься `format.test.js`, змінюється `format.js` — отже, зв'язок є. Класичне
  припущення за назвою замість читання вмісту.
- **Як виправили:** §5 переписано на «почервоніє **рівно один** засіяний тест —
  `test/invoices.test.js:41-42`», плюс окремо зазначено, що
  `test/orders/routes.test.js:49` містить `03/01/2026` як **вхідний** параметр,
  який API має й далі відхиляти з 400.
  **Реальний прогін підтвердив прогноз точно:** 7 червоних, із них 1 засіяний.

**Спіймано до зміни коду.**

## Випадок 3 — тест, написаний для зеленого шляху, повісив прогін на 5 хвилин

- **Що просили:** характеризаційний тест на HTTP-маршрут `/invoices/:number`
  (Task B).
- **Що агент написав:**

  ```js
  test('...', function (t, done) {
    var server = createServer().listen(0, function () {
      get(server, '/invoices/INV-2026-00007', null, function (res, body) {
        assert.equal(body, render.renderInvoiceHtml(invoice, customer));
        assert.match(body, /Сплатити до: <b>03\/21\/2026<\/b>/);
        server.close(done);          // <-- ПІСЛЯ асертів
      });
    });
  });
  ```

- **Чому це помилка:** коли асерт кидає виняток, `server.close(done)` не
  виконується. Listener лишається відкритим, `done` не викликається — і
  `node --test` **висить**.
- **Як помітили:** боляче й не одразу. Перший прогін Task C після зміни коду не
  завершився; його довелося вбити **через 5 хвилин** замість того, щоб побачити
  падіння за 0.45 с. Замість списку червоних тестів я отримав таймаут.
- **Чому агент так вирішив:** тести пишуться в припущенні, що вони проходять.
  Але характеризаційний тест — особливий жанр: його пишуть **саме для того,
  щоб він потім упав**. Падіння тут не аварія, а очікуваний сценарій, і
  прибирання ресурсів мусить бути на нього розраховане.
- **Як виправили:** сервер закривається в `t.after()`, запит загорнуто в
  проміс — тепер падіння завжди видно як падіння:

  ```js
  function listen(t) {
    var server = createServer();
    t.after(function () { return new Promise(function (r) { server.close(r); }); });
    ...
  }
  ```

**Спіймано після того, як нашкодило** — коштувало 5 хвилин і зіпсований перший
прогін Task C.

## Випадок 4 — агент вважав, що знає, які файли підхоплює `node --test`

- **Що просили:** спільний хелпер для golden-майстрів (Task B).
- **Що агент зробив:** поклав його в `app/test/characterization/golden.js`,
  вважаючи, що раннер збирає лише `*.test.js`.
- **Чому це помилка:** Node 22 за замовчуванням підхоплює **будь-який** `.js`
  усередині теки `test/` (патерн `**/test/**/*.?(c|m)js`). Хелпер виконувався
  як тест-файл.
- **Як помітили:** арифметика не зійшлася. 106 засіяних + 22 написані = 128, а
  прогін показував **129**. Перевірка:

  ```
  $ npm test 2>&1 | grep "golden"
  # Subtest: test/characterization/golden.js
  ok 10 - test/characterization/golden.js
  ```

- **Чому агент так вирішив:** переніс звичну конвенцію (`*.test.js`) на
  інструмент, не перевіривши його документацію. Помилку не видно, бо «зайвий»
  файл проходив як зелений — розбіжність в одиницю легко пропустити.
- **Як виправили:** оскільки файл однаково виконується, дав йому корисний тест —
  інвентаризацію golden-файлів, під `if (require.main === module)`, щоб він не
  дублювався в кожному файлі, який робить `require('./golden')`.

**Спіймано до зміни коду.**

## Випадок 5 — агент записав у документ хеш коміту, який сам же зробив недійсним

- **Що просили:** у `docs/impact.md` вказати коміт із характеризаційними
  тестами як доказ, що їх зроблено **до** зміни.
- **Що агент зробив:** вписав `6df56e2`, потім зробив `git commit --amend` —
  хеш став `c95c70f`. Документ почав посилатися на неіснуючий коміт. Після
  подальшого ребейзу (на прохання уніфікувати меседжі) хеш змінився ще раз, на
  `94ce7a8`.
- **Як помітили:** звірка `git log` після amend.
- **Чому агент так вирішив:** сприйняв хеш як стабільний ідентифікатор, хоча
  сам же в тій самій сесії переписував історію. Плюс самореференція: документ
  лежить **усередині** коміту, на який посилається, тож будь-яке уточнення
  тексту змінює хеш.
- **Як виправили:** прибрав хеш; тепер коміт шукається **за вмістом**, що не
  ламається ні від amend, ні від ребейзу:

  ```bash
  git log --oneline --diff-filter=A -- app/test/characterization/golden
  git show --name-only <коміт> | grep app/lib   # порожньо = прод-код не чіпався
  ```

**Спіймано до пушу.**

## Випадок 6 — пастка, у яку агент ледь не вступив: git тихо зіпсував би еталон

- **Контекст:** golden-майстер `oblik-export.csv` існує рівно для того, щоб
  фіксувати контракт із «Облік-Плюс», а в тому контракті **CRLF** — окремий
  пункт (`app/docs/integrations/oblik-plus.md:21`).
- **Що мало статися:** у репо `core.autocrlf=input`. Git при коміті
  переписав би CRLF на LF — тобто зіпсував би саме той байт, заради якого
  еталон і записаний. Тест лишався б зеленим локально й падав на свіжому клоні
  (або, гірше, «виправив» би еталон під хибне значення).
- **Як помітили:** перед комітом перевірив `git config core.autocrlf` замість
  того, щоб припустити типове `false`.
- **Як виправили:** `app/test/characterization/.gitattributes` з
  `golden/** -text`; далі перевірив уже **в blob**, а не в робочому дереві:

  ```
  $ git show HEAD:app/test/characterization/golden/oblik-export.csv | file -
  /dev/stdin: UTF-8 text, with CRLF line terminators
  ```

**Спіймано до коміту.** Це не помилка агента, а пастка середовища — але саме з
таких пасток складається робота з legacy, тому вона тут.

## Що з цього видно

1. **Найнебезпечніша відповідь — та, що збігається з очікуванням.** У випадку 1
   `grep` дав рівно те, що написано в тікеті. Якби агент зупинився на збігу —
   36 рахунків не потрапили б у бухгалтерію, і всі тести були б зелені.
2. **Агент упевнено виводить зв'язки з імен** — файлів (випадок 2), конвенцій
   (випадок 4), ідентифікаторів (випадок 5). Ім'я — це гіпотеза, не факт.
3. **Помилки в тестах коштують дорожче, ніж у коді** (випадок 3): код перевіряє
   тест, а тест не перевіряє ніхто.
4. **Найдешевша перевірка — виконати код.** Один `node -e` із підміною функції
   дав точну відповідь «36 рядків», якої не дало б жодне читання.

> **Про формат здачі.** Це не «контрольний прогін» із шаблону — переключити
> модель на найдешевшу я не міг. Натомість вище шість задокументованих випадків
> із доказами, з них два (3 і 5) встигли нашкодити, а експеримент у випадку 1
> кількісно показує ціну найтиповішої помилки на цьому тікеті.
